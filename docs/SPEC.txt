3. System architecture
Both front ends use one API, and the API enforces consent before any record leaves. The
genetics engine is plain code that computes every risk figure. The agent orchestrator
wraps those figures in approved wording, verifies it, and stops for a human counsellor
when escalation rules fire. The consent and privacy service sits on every read, and the
audit log records each decision. Run all services as containers from one docker compose
up .
Design principles
Deterministic core, model at the edge. Risk figures, tiers and escalation come from
tested code. The model selects among approved template phrases and adjusts reading
level; it never produces a number.

Generator algorithm ( services/cohort/generate.py )
1. Read both configs and seed one random generator; never use global randomness.
2. For each family cluster, create founders with two alleles per condition, using allele
frequency q = carrier_frequency / 2 . For X-linked conditions assign sex and use
the correct allele count.
3. Simulate gametes to build children for the configured number of generations, with
explicit parent links.
4. Form couples: with probability consanguineous_share  pair two descendants of a
common ancestor (weighted so first cousins reach the configured share); otherwise
pair people from different clusters.

5. Genetics engine
The engine ( services/genetics/ ) is pure Python with no network, no model and no wall
clock. It owns every number a person sees. Build it first and test it hardest: a wrong figure
here is the worst failure the product can have. Have a genetics-trained reviewer check the
unit tests before the demo, because the formulas below are standard textbook results
that we have not validated against a clinical source in this project.
Pedigree rules
A person has at most two biological parents (one of each sex at birth) and no cycles;
reject edges that break this.
Edges carry confidence  (known, reported, uncertain). Compute with known and
reported edges; show a warning when uncertain edges exist and offer a recomputation
without them.
Persons with no recorded parents are founders and are treated as unrelated.
Inbreeding coefficient by the kinship recursion. Use the general method; it handles
complex pedigrees where simple path counting fails. Memoise results.
kinship(i, i)   = 0.5 * (1 + F_i)
kinship(i, j)   = 0 if both are distinct founders
for i != j, with i the later-born of the two (order by topological sort):
  kinship(i, j) = 0.5 * ( kinship(father_i, j) + kinship(mother_i, j) )
F_child         = kinship(father, mother)
relationship r  = 2 * kinship(a, b)
Required test values for the coefficient of a child whose parents are: first cousins 1/16;
double first cousins 1/8; full siblings 1/4; half-siblings 1/8; uncle and niece 1/8; second
cousins 1/64; unrelated 0.
Couple assessment per condition. Inputs: both partners' reported status ( carrier ,
not_detected , uncertain ), the condition's inheritance mode, carrier frequency c , test
sensitivity s , and the kinship phi  between the partners.

Autosomal recessive:
  both carrier            -> affected 25%, carrier 50%, neither 25% per 
pregnancy
  one carrier, other not_detected:
     prior_other   = r + (1 - r) * c            # r = 2*phi, chance a 
relative shares the allele
     post_other    = prior_other*(1-s) / ( prior_other*(1-s) + (1-
prior_other) )
     risk_affected = 0.25 * post_other
  both not_detected:
     p_x = c*(1-s) / ( c*(1-s) + (1-c) )  for each partner
     risk_affected = 0.25 * p_a * p_b          # assumes independence; flag 
if related
  any uncertain           -> no figure; status 'needs review'
X-linked recessive, mother carrier: each son 50% affected, each daughter 50% 
carrier
Background risk for an inbred couple, allele frequency q = c/2:
  P(affected child) = q^2 + F * q * (1 - q)     # shown only as context, 
never as a result
The both not_detected  figure ignores correlation between related partners, so the
interface must say that relatedness can raise the true figure and the tier rules must send
related couples to a counsellor when any result is uncertain. Do not invent corrections
beyond these formulas.

6. Agent workflow with LangGraph
Graph 1 turns an incoming screening result into a couple assessment and starts Graph 2.
Graph 2 picks a template, drafts and verifies the explanation, pauses for a counsellor on
tier 3 cases, releases the result, checks understanding with a short quiz, and then tracks
referral to documented closure. Graphs 3 to 5 handle family sharing, the copilot and
evaluation runs.
Design decisions
LangGraph workflow · 5 graphs, 2 human gates

Deterministic routing. Tiers and branches come from the engine and
configs/escalation.yaml , not from a model.
Two kinds of pause. teach_back  waits for the user and counsellor_gate  waits for a
counsellor. Only one is pending at a time in a thread, so each resume is unambiguous.
Several pending interrupts in one run need a resume map keyed by interrupt id (guide),
so keep them sequential.
One thread per couple case. thread_id  is the case id; family sharing runs as its own
thread so a relative's consent never blocks a couple's case.
Durable checkpoints. interrupt()  needs a checkpointer; use SqliteSaver  locally
and PostgresSaver  for the demo stack, and resume only with Command(resume=...)
(overview).
Current APIs. LangGraph and LangChain reached 1.0 in October 2025 and
create_agent  in langchain.agents  replaces create_react_agent  (LangChain). Pin
versions and check docs.langchain.com before coding.

def counsellor_gate(state: CaseState) -> Command:
    # No side effects above interrupt(): a resumed node restarts from its 
first line.
    decision = interrupt({"case_id": state["case_id"], "draft": 
state["draft"],
                          "assessment": state["assessment"]})
    return Command(update={"counsellor_decision": decision}, goto="release")
def teach_back(state: CaseState) -> Command:
    answers = interrupt({"case_id": state["case_id"], "quiz": state["quiz"]})
    return Command(update={"quiz_result": grade(state["quiz"], answers)})

Referral state machine ( ReferralState ). Allowed transitions only; each has an owner
and a due date from configs/escalation.yaml , and each change writes an audit event.

counselling_done -> confirmatory_requested -> confirmatory_done

Timers. A scheduler calls the API at due times, and the API resumes or updates the thread

7. Agents and LangChain components
Use the model where wording and retrieval help, and make every number and every
medical statement come from code or reviewed text. LangChain 1.x supplies the agent
loop, structured output and middleware; LangGraph supplies the durable workflow;
LangSmith supplies traces and evaluation (LangChain, overview). Evidence says models
that simplify text can drop critical information and that readability gains can cost
accuracy (simplification study, RepQA), so the design limits what the model may write.

2. Couple pooling needs both. A couple assessment uses both partners' results, so

reveal that the other person declined.

5. Deletion. Provide DELETE /api/me , which removes the person, relationships, results

inventory test lists routes and fails if one is added.
7. No unrelated use. The policy has no purpose code for employment, insurance or
commercial use, so such reads are always denied; the governance page says so.

Rules for the coding agent
1. Read this whole spec first, then work phase by phase. Put the task id in every commit
message, for example P1-3: kinship recursion .
2. Never use real genomes or real personal data. Every row is synthetic and flagged;
every source is listed in DATA_SOURCES.md .
3. Every number a person sees comes from services/genetics . No agent, template slot
or front-end code may compute or invent a risk figure.
4. Keep services/genetics  pure: no network, no model, no wall clock, no randomness
except through an explicit seeded generator in services/cohort .
5. Every read of personal data goes through decide() . Add a test whenever you add a
route or tool.
6. The model never writes free-text medical statements in Mode A. In Mode B it only
rewrites approved blocks and the verifier gates the result.
7. Put thresholds, tiers, panel, languages, escalation rules and flags in configs/ . No
magic numbers in code.
8. Do not mark any template or Arabic string approved until the reviewers are recorded in
docs/REVIEWS.md . Machine-translated text is allowed only as a placeholder and must
be flagged.
9. Write tests before or with each function in the engine, consent and verifier packages.
Use property tests where the spec lists them.
10. Gate every optional feature behind a flag. Run make demo  before closing any task; the
demo path must stay green.
11. Label fictional data in code, API responses and UI. Never write wording that steers a
couple's decision or labels people, families or communities.
12. If a library API differs from this spec, follow the installed version and record the
difference in docs/DEVIATIONS.md .
13. If something is ambiguous, choose the simplest safe option, record the question in
docs/OPEN_QUESTIONS.md , and continue.
Definition of done for a task. Code merged with tests; CI green; docs or config updated;
the acceptance check in section 10 passes; make demo  runs.
